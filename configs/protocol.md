# Протокол неявной адаптации до измерений

Проект задания 3, редакция 19.11.2026. Этот файл задаёт будущую процедуру и не подтверждает выполнение новых запусков. SHA256 байтов experiment.json: `f9258eeedb63e625aaa3331367589193c1976dd79014b1dc8df755b86247a705`. Canonical config digest, как в runtime `adaptation.digest`: `e85364be8866628bf0b6e11cd9ec95510e9893c76443a70000f65ccb43b09b89`. Копия протокола, конфигурации, prompt и исходников сохраняется до чтения итоговых сравнений.

RQ: повышает ли выбор LLM по хронологической истории осмотра недвижимости покрытие трёх скрытых актуальных потребностей относительно static, включая смену интереса?

Основной исход C = |selected_fields ∩ required_fields|/3. D = C_llm − C_static, парность по scenario/seed. Для каждого сценария H0: E(D) ≤ 0.20; H1: E(D) > 0.20. Порог 0.20 выбран автором как инженерный, не взят из публикаций. Поддержка практического преимущества: нижняя граница отдельного 95% paired percentile-bootstrap CI > 0.20; 5000 перевыборок пар со seed 4210. Дополнительный exact two-sided sign-flip перебирает 2^10 знаков и проверяет нулевую разность при обменности знаков. Holm корректирует два p в одном запуске при α=.05; этот тест не проверяет практический порог. Публикуются D, CI, все десять разностей, raw/adjusted p, dz либо null при нулевой дисперсии.

Факторы: static/llm × focused/shift × 10 seeds 4210–4219. Один полный запуск: 40 main contexts и 5 static A/A-пар, всего 50 contexts. A/A использует focused seeds 4210–4214 и не увеличивает n main. Порядок jobs перемешивается seed 4210. Второй полный свежий запуск повторяет seeds и тот же порядок, делает ещё 20 новых LLM-попыток; серии анализируются отдельно, без объединения в n=20. При доступном API бюджет двух запусков составляет 40 реальных HTTP-вызовов; локальные ошибки ключа не считаются такими вызовами.

Каталог: шесть объектов, девять полей; static = price/area/rooms, cards. LLM выбирает ровно три различных допустимых поля и cards/comparison. Общий renderer, viewport 1280×900. Каждый context свежий; перед сбором история начинается в DEFAULT. История содержит 18 фактических DOM-inspections, dwell 2500–7000 мс задаётся программно без реального ожидания. В shift первые 6 событий относятся к старой тройке, последние 12 к актуальной; индексы 4 и 13 добавляют постороннее поле. Comparison моделируется возвратами к p0/p1/p2, cards последовательным просмотром шести объектов. Шесть латентных профилей заданы в runner/experiment.py, не являются наблюдениями людей.

Request содержит только events и общий system prompt; required_fields/required_view и scenario не передаются. Модель nvidia/nemotron-3.5-lightning:free, temperature 0, max_tokens 700, seed 4210, reasoning disabled, timeout 90 с. Fine-tuning не выполняется. Retry нет, при сбое сохраняются error/response и DEFAULT с valid=false; этот исход входит в основную оценку. Закреплённый model ID не гарантирует идентичного внешнего backend. Сохраняются request, response, usage, latency и prompt hash; ключ не сохраняется. Отсутствующий cost, преобразованный парсером в 0, не трактуется как измеренная бесплатность.

Вторичные метрики: правильность вида; реальные DOM-клики для извлечения трёх полей у трёх объектов; browser_ms после применения схемы без API и сбора истории; latency/tokens/сообщённый cost API, ошибки схемы/браузера/значений. Если нужно сравнение, а выбраны карточки, runner открывает таблицу; обратного переключения, когда нужны карточки, не требует. В comparison столбец открывается сразу для всех объектов, в cards отдельно. Это рецепт автоматизации, не время человека и не исследование usability.

Перед main: smoke values, известный маршрут 3 клика, cold DEFAULT 0 кликов, отклонение неправильной schema, генерация 10000 историй. Прогрев выполняется на отдельной странице и исключён из эффекта; обучения LLM нет. A/A ожидает нулевые разности покрытия/кликов, время описывается с CI, без заявления эквивалентности по p>.05. CPU runner/Chromium усредняется cgroup за прогон с ожиданием API; средний headroom не исключает пиков и влияния генератора.

Артефакты каждого запуска: config.json, prompt.txt, environment.json, calibration.json, raw/*.json, manifests/*.json, per-run.csv, summary.json, figures. Требования целостности: 50 raw, 40 main, 20 LLM-попыток, 10 пар на scenario, совпадение последовательности полей/объектов и синтетического dwell в паре, при разных часовых отметках, SHA256 raw, отсутствие labels в request, browser_errors=0, wrong_values=0. Недоступность API и fallback публикуются, не исключаются. При повреждении данных сохраняется неудачный пакет и выполняется новый полный запуск после исправления.

Повторный анализ из сохранённых raw должен давать coverage, CI и p с допуском 1e−12. Static coverage/view/clicks при тех же входах совпадают точно. Ответы LLM между свежими запусками могут различаться; расхождения сообщаются. Для времени не задаётся произвольный процент допуска. Девять уровней проверки и команды приведены в REPORT.md. Архивировать dirty-копию необходимо целиком: Git SHA и dirty-флаг не заменяют diff.

Нет независимого закрытого test split и эвристического baseline. Вывод ограничен синтетическим каталогом и выбранной API-стратегией; превосходство LLM над правилами, человеческое удобство, SUS/NASA-TLX и результаты user study не заявляются. Exploratory Spearman времени с порядком и сравнение двух серий не меняют исходную гипотезу после просмотра данных.
